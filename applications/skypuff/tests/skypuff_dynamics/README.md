# SkyPUFF drum and airborne-rope model

## Current linear controller with acceleration holds

`rate_transitions.py` compiles the current production C code and couples it to
the existing cable/drum model. It uses nominal 100 kgf, glider speed +6 m/s,
1500 m of rope, the 15 kg / 250 mm drum, a -3 m/s² hold threshold and quantized
tachometer readings. Step/filter periods are extracted from the current source.

```sh
python applications/skypuff/tests/skypuff_dynamics/rate_transitions.py --cc gcc \
  --case pull_unwinding --output build/skypuff_rate_100kg_glider6_off3/pull_unwinding
```

Other cases: `unwinding_pull`, `pre_pull_manual_braking`, `pull_manual_braking`.
For `unwinding_pull`, the user explicitly chose free space below the drum:
at 2.2 kgf the initial catenary dips about 58 m below it, so ground contact does
not stop this case. It uses 240 cable segments, checked against 480. The intact
rope model stops at the catalogue strain limit of 3.15%; it does not simulate
rupture or motor speed/power limits. Other cases stop at first ground contact. The independent
antisex current correction and FSM strong-Unwinding target changes are omitted;
the production smooth-current hold uses the filtered acceleration.

## Previous stage-based controller

After the firmware rollback, `closed_loop.py`, `tune_feedback.py`, and the C bridge
still target the previous stage-based controller and cannot compile against the
restored rate-based implementation. Existing saved results remain historical
simulations. For current PrePull / Unwinding setpoint plots, use
`../skypuff_smooth/plot_rate_transitions.py` as described in its README.

This is an offline mechanical simulation. It does not change firmware, flash,
or winch configuration. The input is the **actual production C controller trace**
for `pull_manual_braking` generated by `applications/skypuff/tests/skypuff_smooth/run_tests.py`.

## Scenario

- Nominal Pull: 140 kgf; PrePull: 42 kgf; TakeoffPull: 91 kgf; FastPull: 175 kgf.
- `smooth_motor_p = 1`: directly 140 → 1.8 kgf over 2 s of active ramp time.
  Without acceleration pauses, the controller switches to braking at 2 s.
  PrePull is not an intermediate target. With feedback, pause time is added.
- Drum mass: 15 kg, radius: 0.125 m. The main case places the mass at the rim:
  `J = m R² = 0.234375 kg m²`. A solid-cylinder alternative uses half that inertia.
- Initial drum surface speed: +7 m/s (reeling in), about 535 rpm.
- The glider is a prescribed moving boundary, travelling towards the winch
  at 7 m/s **along the winch–glider chord**. Its speed does not react to tension.
  No pilot mass, wing aerodynamics or flight dynamics are inferred.
- Initial airborne cable **stretched arc length**: 1500 m. Chord angle: 15°.
  The local exit angle at the drum differs because of sag.
- Cable diameter: 1.7 mm. The chosen catalogue analogue is Armare Dynext PU,
  a single-braided Dyneema SK75 rope. The user's exact product is unknown.

## Sourced rope properties

[Armare Dynext PU product table](https://store.armareropes.com/eng/dynext-pu-dyneema-sk75.html)
gives **1.70 g/m** and a breaking load of **287 daN = 2870 N** at 1.7 mm.

[Armare Diving catalogue 2021, printed page 8](https://store.armareropes.com/pub/media/mageworx/downloads/attachment/file/cataloghiArmare/2021/armare-diving-line-ita.pdf)
gives these extension points for Dynext PU:

| Tension | Strain |
| --- | --- |
| 30% of breaking load = 861 N | 1.95% |
| Breaking load = 2870 N | 3.15% |

The model joins `(0, 0)` and these two points by straight segments. This gives
axial tangent stiffness **EA = 44.15 kN** below 861 N and **EA = 167.42 kN** above
861 N. These are **derived cable stiffnesses**, not a quoted fibre Young modulus.
The diameter is not treated as the area of a solid polymer cylinder.

Interpolation, the zero-load origin, and reversible unloading along this same
curve are modelling assumptions. The catalogue does not supply an unloading
loop, dynamic modulus, creep law or internal damping. Constructional stretch
may not be fully recoverable. Thus this model illustrates a catalogue-based
elastic response; it is not a calibrated prediction for a used winch rope.

Internal axial damping is separately parameterized as `BA = 200 N s`, with
50 and 800 N s alternatives. These damping values are **assumed**, not sourced
measurements. All alternatives retain the same sourced strain points.

## Equations

Let `r(s,t)` be cable position, `U` its material velocity, `mu` its mass per
unstretched metre, and `s` unstretched material coordinate. In the vertical plane:

```text
mu * D(U)/Dt = d(T * tangent)/ds + mu * (0, -g)
strain = |dr/ds| - 1
T = max(T_elastic(strain) + BA * D(strain)/Dt, 0)
```

A slack segment (`strain <= 0`) carries no tension. The cable cannot push.
The cable is divided into 120 equal unstretched segments, with gravity and
mass distributed along the rope; it is not replaced by one massless spring.
The spring/damper/node discretization is the standard approach described in
[MoorDyn's line model](https://moordyn.readthedocs.io/en/latest/structure.html).
This implementation is independent; it does not call or claim MoorDyn validation.

Reeling changes the unstretched airborne length `L`. A uniform moving grid uses
`xi = s/L`, with its lower material boundary advancing as rope is taken in:

```text
feed = v_drum / local_stretch_ratio
L_dot = -feed
b = feed * (1 - xi)
grid_position_dot = U + b * dr/ds
U_dot_on_grid = material_acceleration + b * dU/ds
```

These transport terms distinguish material motion from grid motion. The drum
exit stays at `(0,0)`; material velocity there is `-v_drum * tangent`. The far
endpoint moves along the initial chord at 7 m/s. Cable mass in the free span
changes with `L`. Drum radius and inertia remain constant, neglecting the small
amount of rope transferred during this short transition and any reflected motor
or gearbox inertia.

At the drum, tension creates opposing torque `R*T`. Positive drum rotation
winds rope in:

```text
J * omega_dot = R * (F_motor - T_at_drum)
v_drum = R * omega
a_drum = (F_motor - T_at_drum) / (J/R²)
```

The C trace's equivalent kgf is converted to force using `g = 9.80665 m/s²`.
Before brake mode, `F_motor = command_kgf * g`, even if the drum reverses.
In brake mode, an ideal passive brake opposes rotation:

```text
F_motor = -brake_kgf * g * tanh(v_drum / 0.02 m/s)
```

The narrow smoothing around zero speed avoids numerical chatter. Actual VESC
commutation, zero-speed shorting, electrical limits, torque ripple, bearing
friction, motor saturation and torque-vs-current errors are not simulated.
The orange command curve shows the **brake magnitude**; it is not signed force
or measured rope tension. Signed motor force is included in the CSV output.

## Initial conditions and validity

The initial static shape solves the discrete elastic catenary exactly: the
vertical component of adjacent segment forces differs by the intervening weight.
Drum tension starts at 140 kgf, the arc length at 1500 m, and the chord at 15°.
Neighbouring static solutions initialize the material velocities consistently
with both moving boundaries. The constant-Pull regression checks that artificial
startup oscillations are negligible.

The initial unloaded span is shorter than 1500 m because the rope is already
stretched. Its mass is consequently slightly below the simple `1500 * 1.70 g/m`
estimate. Separate static figures show equilibrium for all four pull levels;
each has an initial 1500 m stretched arc and a 15° chord.

Only gravity and internal axial damping are included. There is no wind, air
drag, cable bending stiffness or contact/friction with the ground. Ground level
is assumed equal to the drum exit. **Simulation stops at the first interior
node touching that level.** Data after contact are not extrapolated through the
ground. A different fairlead height, terrain or aerodynamic load changes this
end time. Slack is explicitly allowed before contact.

Antisex feedback is disabled. A separate curve applies the speed/acceleration
filter equations from `measurement_tick` to ideal drum motion: two adjacent
sample averages plus first-order filtering, sampled every 5 ms. The filter
period comes from the controller trace report (currently 50 ms; legacy reports
without this setting use their original 50 ms). Filters
are initialized to the established 7 m/s. Tachometer quantization is omitted.

## Run and outputs

Requires Python 3, NumPy and Matplotlib. First generate the production-controller
trace (standard library + GCC; plotting that trace is optional):

```sh
python applications/skypuff/tests/skypuff_smooth/run_tests.py --cc gcc \
  --output build/skypuff_smooth_direct_140kg --pull-kg 140 \
  --pull-ms 4000 --brake-ms 2000 --pre-k 0.3 --takeoff-k 0.65 --fast-k 1.25 \
  --amps-per-kg 2.45 --unwind-kg 2.2 --strong-kg 5.2 --brake-kg 1.8
python applications/skypuff/tests/skypuff_dynamics/run_simulation.py
```

`--control-dir` selects the C trace directory. `--output` selects the mechanical
results directory, default `build/skypuff_dynamics_direct_140kg`. `--skip-convergence`
skips the extra numerical convergence runs; it does not skip algebra checks.

Files include PNG/SVG figures, the main time-series CSV, alternative-case CSVs,
rope-coordinate snapshots, and `results.json` with parameters, sources,
controller settings, a SHA-256 of its input CSV, metrics and verification results.

- `pull_manual_braking_dynamics`: commanded force, rope tension, drum velocity
  and acceleration on three adjacent axes.
- `rope_equilibrium_and_stiffness`: gravity sag at four pull levels and the
  catalogue-based force/strain law.
- `damping_and_inertia_sensitivity`: dependence on assumed internal damping and
  on rim-mass versus solid-cylinder drum inertia.

Verification checks the two catalogue points, no compressive cable force,
static nodal balance, non-positive brake power, steady operation before a
command change, halved time step, and doubled spatial resolution. Numerical
convergence does not validate the assumed rope hysteresis, damping, motor model
or imposed glider motion against hardware.

## Acceleration feedback: pausing smooth_motor

### Offline parameter tuning and tachometer quantization

`tune_feedback.py` varies the update interval, shared filter period and an
experimental resume hysteresis **only in generated host includes/settings**.
Production firmware is not changed. `plot_tuning.py` compares the saved trials.
The tuning score uses physical acceleration over 10–90% of the current reduction:
standard deviation, 5th/95th percentiles, and RMS error relative to the pause
threshold. A smoother filtered signal alone is not treated as an improvement.

For example, with the 100 kgf input report from the host tests:

```sh
python applications/skypuff/tests/skypuff_dynamics/tune_feedback.py --cc gcc \
  --control-dir build/skypuff_step100_filter25_100kg \
  --output build/skypuff_feedback_tuning/100kg_s20_f50_h0_encoder \
  --step-ms 20 --filter-ms 50 --tachometer-step-mm 7.999425738307205
```

`--tachometer-step-mm` enables optional encoder quantization. Zero preserves
the previous ideal continuous-distance measurement. `--phase` selects the
fractional encoder position at the command; the filters are warmed up with one
second of steady motion at the initial drum speed (7 m/s by default). The 5 ms displacement integral is converted to
integer counts before applying the production filter equations.

`--start-state pull` starts at nominal pull; the default `fast_pull` starts
at `fast_k * pull_kg`. The same initial current initializes both the C controller
and the cable equilibrium. For a single nominal pull, use
`plot_tuning.py OUTPUT --nominal-kg 140`; it reads the three matching
`140kg_s{step}_f{filter}_h0_encoder` trials and plots setpoint, speed, physical
acceleration and filtered acceleration.
Add `--case 20 50` to show only that selected step/filter pair; the force panel
then also shows cable tension and shaded current-hold intervals.

`--glider-speed-mps -1` imposes steady motion away from the winch along the
initial chord. It initializes both drum speed and measurement filters to that
same signed speed; there is no artificial +7 to -1 m/s startup transient.
Negative drum speed is rope payout. The existing signed acceleration threshold
is unchanged, so negative acceleration during payout means increasing payout
speed. Wind is represented only by the imposed glider motion; aerodynamic loads
on the rope or glider are not added.

The inspected INI has wheel diameter 275 mm, ratio 4.5 and 8 motor poles, giving
`pi * 275 / (4.5 * 8 * 3)` = approximately 8 mm per tachometer count. This is
used as a measurement-resolution estimate; the requested mechanical drum
diameter remains 250 mm. A calibration scale error is not included. Neither
electronic noise nor missed counts are included. Historical plots did not
include encoder quantization, so compare tuning cases with matching encoder
settings. The threshold defaults to -1 m/s² in these host trials;
`--acceleration-off-mss -2` selects another threshold without changing firmware
or the INI file.

The actual production `measurement_tick` function was also checked with
quantized constant-speed motion. At 7 m/s and this count size, the 25 ms filter
produces approximately -2.72 to +2.78 m/s² despite zero physical acceleration;
the 50 ms filter reduces this to approximately -0.68 to +0.82 m/s². These are
results for that speed and resolution, not universal noise limits.

### Closed-loop simulation

`closed_loop.py` couples the same mechanical model directly to compiled production
`smooth_motor` functions through `controller_bridge.c`. It no longer uses a
prerecorded command for this experiment: simulated speed is measured every 5 ms,
filtered with the `measurement_tick` equations, and fed back to the C controller.
The mechanical integration step is at most 0.25 ms (reduced for shorter segments),
and the host control loop is 1 ms.
Setpoint updates use the firmware's `smooth_max_step_delay = 20 ms` (50 Hz).
The measurement interval and shared speed/acceleration filter period are read
from production code: currently 5 ms and 50 ms, giving a filter gain of 0.1.
The separate antisex current correction remains disabled.

The controller uses `config.antisex_acceleration_off_mss`, the existing
`[antisex] acceleration_off_mss` INI parameter in m/s². During a ramp that
reduces current magnitude, acceleration below that value holds the current and
freezes the curve at the last applied point. The stage clock excludes the held
interval. Resume requires acceleration strictly above the threshold; equality
preserves an existing hold. A newly resumed update returns the held point, then
subsequent updates advance the curve. No elapsed pause time is caught up.
Both signs of current use this rule. Rises, instant low-current
brake requests, release, speed control and the braking/slowing zone overrides
retain their existing behavior. The same configured threshold is shared with
antisex; the flash configuration layout is unchanged. The fixture defaults to
-3 m/s², matching `set_example_config` and the INI.

This is a hold rule, **not a hard bound on physical acceleration**. Filtering,
20 ms command updates, inertia and cable response allow acceleration to fall
below the configured threshold even after the setpoint has stopped decreasing. No hysteresis band
or active current increase is added.

First run the host controller tests with the 140 kg settings and output directory
above, then:

```sh
python applications/skypuff/tests/skypuff_dynamics/closed_loop.py --cc gcc
```

To calculate another threshold without changing the firmware source, use a
separate output directory, for example:

```sh
python applications/skypuff/tests/skypuff_dynamics/closed_loop.py --cc gcc --acceleration-off-mss -2 \
  --output build/skypuff_dynamics_direct_minus2
```

`--acceleration-off-mss` sets the existing field in the host C configuration.
Without the flag, the setting comes from the controller test report; legacy
reports without this field use -3 m/s². The report records the effective setting
and any host config override alongside the source hash. Firmware constants are
not rewritten for these calculations.

The default output is `build/skypuff_dynamics_configured/`. It contains:

- `pull_manual_braking_acceleration_pause.png/.svg`: force, speed and acceleration,
  compared with the same model without feedback pauses.
- `acceleration_pause_first_seconds.png/.svg`: first 3 seconds at higher detail.
- `with_pause.csv`, `without_pause.csv`: command, motor mode, mechanical state,
  filtered measurements and pause status on a 5 ms grid.
- `results.json`: exact source hash, parameters, pause/resume events, completion
  times and convergence checks; plus CSVs for the finer step and grid.

The maximum simulation duration is controlled by `--end` (30 s by default).
`--start-state pre_pull` starts in current control at `pre_k * pull_kg`, while
retaining `pull_kg` as the nominal pull in the C configuration. This distinction
keeps the PrePull boundary correct. A decrease from exactly PrePull is smooth:
PrePull → Manual_braking ramps directly to the brake magnitude over
`braking_applying_period` plus acceleration pauses, then enters brake mode.
Growth up to PrePull remains instantaneous, as do new low-current brake requests
starting strictly below PrePull with a brake magnitude at or below PrePull.
The initial cable equilibrium is solved at PrePull. Its figure is saved as
`pre_pull_manual_braking_acceleration_pause.png/.svg` and compares the transition
with and without feedback pauses. After switching modes, the command represents
brake magnitude, with physical torque opposing rotation. For example:

```sh
python applications/skypuff/tests/skypuff_dynamics/closed_loop.py --cc gcc \
  --control-dir build/skypuff_smooth_direct_100kg --start-state pre_pull \
  --acceleration-off-mss -3 --rope-length-m 1500 --output build/skypuff_pre_pull_100kg_1500m
```

`--rope-length-m` sets the initial stretched airborne length (1500 m by default).

For one FastPull → Unwinding curve with measured acceleration feedback, use
`--start-state fast_pull --target-state unwinding --acceleration-off-mss -1`.
The model starts in equilibrium at `fast_k * pull_kg`; the controller retains
the nominal Pull configuration and receives one fixed `unwind_kg` current target.
There is no strong-Unwinding target change and no switch to brake mode. The
curve takes `pull_ms` of active time plus feedback pauses. The figure and report
record completion time, or say that ground contact stopped the model first.
For example:

```sh
python applications/skypuff/tests/skypuff_dynamics/closed_loop.py --cc gcc \
  --control-dir build/skypuff_smooth_config_off_100kg \
  --start-state fast_pull --target-state unwinding --acceleration-off-mss -1 \
  --rope-length-m 1500 --output build/skypuff_fast_unwind_100kg_1500m_off1
```

For example, pass `--rope-length-m 700 --acceleration-off-mss -3` with the desired `--control-dir`
for the 100 or 60 kgf case, and a separate `--output` directory. The initial
equilibrium is solved again for that length; mass, sag and axial compliance change
with it. The integration step is automatically halved as needed for the shorter
segments' wave and damping time scales, and recorded in `results.json`.
Each run still stops at its own first contact with ground at drum-exit height;
the baseline therefore ends before the feedback run. No curve is extended
past its model's contact event. `--skip-convergence` skips the two additional
resolution checks, but still checks the pause/resume behavior of the coupled run.
